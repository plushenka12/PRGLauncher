# HowLongToBeat у PRGLauncher

## Рішення

HLTB має стати найближчим великим етапом **до Multi-Launcher Foundation**. Це підсилює всі наявні картки одразу — Steam, Nintendo і вручну додані ігри — та не залежить від того, де саме гра була придбана.

Продуктовий результат: у вікні інформації про гру, одразу після особистих сесій, з’являється компактний блок **HowLongToBeat**:

| Поле | Приклад |
|---|---|
| Твій час | `13 год 20 хв` |
| Main Story | `15 год` |
| Main + Extras | `21 год` |
| Completionist | `33 год` |
| All Styles | `22 год` |

Блок містить `Відкрити HowLongToBeat`, дату оновлення, кнопку `Змінити матч` і можливість приховати HLTB для конкретної гри. HLTB не має змінювати статус гри автоматично: `Completed` визначає користувач, а не середній час спільноти.

## MVP реалізовано 13.09.2026

У PRGLauncher вже є перша локальна experimental-версія:

- блок з'являється після журналу сесій у `Game Info` лише коли відкрито конкретну гру;
- показує `Main Story`, `Main + Extras`, `Completionist` та `All Styles`;
- точний збіг назви прив'язується автоматично, а всі неоднозначні результати відкривають вибір версії; користувач може шукати під іншою назвою;
- доступні `Відкрити HLTB`, `Оновити HLTB`, `Змінити збіг` та `Сховати HLTB` для однієї гри;
- прив'язка і результат кешуються 30 днів, невдалий запит — 10 хвилин; бібліотека ніколи не сканується у фоні;
- запити відбуваються локально в ізольованому прихованому вікні Electron. PRGLauncher не передає назви ігор на свій сервер, не просить HLTB-акаунт і не зберігає токени HLTB.

Інтеграція навмисно лишається experimental: HLTB може змінити внутрішній web-протокол. У такому разі картка й усі сесії продовжують працювати, а блок запропонує спробувати оновлення пізніше.

## Що показує готовий Steam Deck-приклад

Відкритий плагін [HLTB for Deck](https://github.com/hulkrelax/hltb-for-deck) показує саме корисний мінімум: чотири основні показники HLTB на сторінці гри, перехід на сторінку HLTB, приховування за грою та локальний кеш на дві години. Це хороший UX-референс, але не готовий backend для PRGLauncher. [README плагіна](https://github.com/hulkrelax/hltb-for-deck)

Його важливі рішення варто повторити:

- дані не заважають відкрити картку, якщо мережі немає;
- кожна гра може приховати блок HLTB;
- користувач бачить тільки потрібні типи часу;
- результат кешується, а не запитується щоразу при рендері.

## Технічна реальність HLTB

HowLongToBeat не публікує стабільний офіційний API для сторонніх застосунків. Community-клієнти виконують пошук за назвою через внутрішні web-запити. Наразі сайт використовує динамічні ключі/tokens: сучасний Node-клієнт окремо витягує їх, кешує й оновлює після помилки. Це пояснює, чому старі плагіни час від часу перестають працювати після зміни HLTB. [jvc-hltb: механіка dynamic token](https://github.com/javocsoft/nodejs-jvc-hltb), [приклад зламаних HLTB плагінів після змін сайту](https://www.reddit.com/r/playnite/comments/1ru0odr/howlongtobeat_extension_not_working/)

Тому HLTB не можна оформлювати як гарантований хмарний сервіс PRGLauncher. Є два правильні варіанти:

1. **Найкращий для релізу:** звернутися до HowLongToBeat / IGN із запитом на дозвіл або ліцензований API для read-only metadata.
2. **Локальна experimental-інтеграція:** не відправляти назви бібліотек на сервер PRGLauncher, запитувати HLTB тільки з ПК користувача, кешувати рідко, забезпечити вимикач і не ламати лаунчер, якщо HLTB змінив внутрішній протокол.

Другий варіант технічно можливий, але перед включенням у широкий реліз треба перевірити актуальні умови HLTB. Не використовувати обхід captcha, автоматичний браузерний harvesting або великий фоновий обхід всієї бібліотеки.

## Як PRGLauncher має це реалізувати

### 1. HLTB metadata adapter

У main process створюється ізольований сервіс:

```js
lookupHltb({ title, year, platforms, force }) => {
  candidates: [{ id, title, year, image, main, extra, completionist, allStyles }],
  match: { id, confidence, ... } | null,
  sourceUrl,
  fetchedAt
}
```

Renderer не ходить напряму на HLTB: він викликає тільки preload IPC. Так не з’являються CORS-проблеми, не витікають токени в DOM, а логіка retry/rate-limit лишається в одному місці.

### 2. Надійне зіставлення гри

Не підставляти перший результат за назвою. Потрібен score:

- нормалізована назва: прибрати `™`, `®`, `Game of the Year`, зайві edition words;
- врахувати рік релізу, коли він є;
- врахувати platform hint: PC, Switch, PS4/PS5, Xbox;
- покарати DLC, demo, soundtrack, guide, remaster та інші неосновні results;
- автоматично приймати лише високий score; у сумнівному випадку показати 3–5 карток і кнопку `Не знаходити для цієї гри`.

Для вже прив’язаного `hltbId` нові запити робити за ID, не за назвою. Це критично для назв на кшталт `Doom`, `Prey`, `Persona 5`, `Final Fantasy VII` і для різних edition.

### 3. Кеш і ліміти

- Кешувати позитивний match локально **30 днів**; HLTB-оцінки змінюються, але не щогодини.
- Negative cache для `не знайдено` — 7 днів, щоб не бити по API на кожному відкритті.
- Не запускати запит на кожен render або при старті програми.
- Автоматично запитувати лише коли користувач вперше відкрив картку або коли запускає команду `Оновити HLTB`.
- Обмежити чергу, наприклад одна активна операція та пауза між запитами.
- При `429`, token error, captcha або network error: припинити чергу, показати зрозумілий статус і спробувати знову лише вручну/пізніше.

Такий підхід схожий на HLTB for Deck, який кешує результати й дозволяє очистити кеш, але більш ощадливий для застосунку з великою бібліотекою. [HLTB for Deck features](https://github.com/hulkrelax/hltb-for-deck)

### 4. Дані у картці

```js
game.hltb = {
  id: 12345,
  matchedTitle: 'Example Game',
  confidence: 0.96,
  mainStoryMinutes: 900,
  mainExtraMinutes: 1260,
  completionistMinutes: 1980,
  allStylesMinutes: 1320,
  sourceUrl: 'https://howlongtobeat.com/game/12345',
  fetchedAt: 0,
  hidden: false,
  manualMatch: false
};
```

HLTB — це спільна metadata, не приватні дані користувача. На першій версії зберігати кеш локально й синхронізувати в PRG Account тільки user decisions (`hltbId`, `hidden`, manual match), а не робити HLTB дані частиною public dashboard. Це зменшує навантаження і не перетворює Firebase на копію чужої бази.

### 5. Інтерфейс

У Game Info після `Sessions`:

```text
HOWLONGTOBEAT                         [↗ Відкрити] [⋯]
Main Story       15 год       Твій час: 13 год 20 хв
Main + Extras    21 год       До Main: ~1 год 40 хв
Completionist    33 год
All Styles       22 год
```

Меню `⋯`:

- Оновити дані HLTB;
- Змінити матч;
- Приховати HLTB для цієї гри;
- Очистити зв’язок.

Для статусу Backlog можна показати `~15 год до фіналу` лише як тонкий supplementary badge. Ніколи не показувати його як дедлайн або «залишилося», якщо користувач не вибрав Main Story як власну ціль.

## Складні випадки

| Випадок | Поведінка |
|---|---|
| Гра не знайдена | `HLTB: даних немає`, ручний пошук, negative cache |
| Ремейк / remaster / edition | Показати вибір кандидатів, не матчити автоматично |
| DLC / demo / app | За замовчуванням HLTB не шукати |
| Онлайн-гра без фіналу | Показати `немає однозначної Main Story`, не ламати блок |
| Користувач грає через Steam і Switch | Один HLTB match для об’єднаної PRG картки |
| HLTB недоступний | Картка лишається робочою; показати останній кеш або нейтральний стан |
| Неправильний автоматичний збіг | `Змінити матч` і запам’ятати user choice |

## Чого не робити

- Не робити bulk-запит на сотні ігор при старті.
- Не автоставити Completed, якщо твій час більший за HLTB Main Story.
- Не вимагати HLTB-акаунт або пароль.
- Не використовувати дані HLTB для реклами, рейтингу користувачів або public dashboard без окремого дозволу.
- Не ховати помилку матчінгу: користувач має бачити назву HLTB гри та мати швидку заміну.

## Порядок реалізації

1. Винести HLTB metadata model і UI block без мережевих запитів.
2. Реалізувати ручний пошук та прив’язку кандидата; це дає корисність навіть до автоматичного matcher-а.
3. Додати локальний lookup, TTL cache, error states і rate-limit.
4. Додати auto-match для високої впевненості та manual override.
5. Додати пакетне, але добровільне `Знайти HLTB для N ігор` з видимим прогресом і можливістю скасувати.
6. Лише після стабільного тесту вирішити, чи функція входить у основний реліз, чи лишається Experimental через відсутність офіційного API.
